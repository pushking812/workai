# Этап 1. Что реализовано

Ядро без GUI: берёт папку с Word-документами, читает штамп, считает хэш,
определяет версию документа, извлекает таблицы в CSV и пишет всё в SQLite.

## Запуск

```
pip install -r requirements.txt
python main.py ВОР                 # прогон папки, результат в data/app.db
python main.py ВОР --db my.db      # другая база
python -m pytest -q tests          # тесты
python convert_doc.py КЖ СО        # .doc -> .docx, разбор штампа, лист на папку в vor_parsing_results.xlsx
```

`main.py` только вызывает `scripts/process_folder.py`. Прогресс по файлам
(`[N/M] имя ... результат, CSV: K`) идёт в stderr; в stdout печатается только
итог: число файлов по статусам, папка CSV и ошибки. Таблица штампов пишется в
`data/exports/_report_<папка>.tsv` (utf-8-sig, табуляция); в консоль она
выводится с флагом `--verbose`. Если запись с тем же хэшем и путём уже есть,
файл получает `ALREADY_EXISTS` (реквизиты берутся из БД), CSV при этом
перезаписываются. Чтобы пересчитать штамп, удалите старую БД или задайте
новую через `--db`. Файлы `.doc` читаются
через Microsoft Word (pywin32); без Word такой файл получает
`stamp_status = UNSUPPORTED`. Тест записи в xlsx требует, чтобы
`vor_parsing_results.xlsx` был закрыт в Excel.

## Структура

| Файл | Назначение |
|---|---|
| `core/database.py` | SQLite, таблица `files`: `init_db`, `add_file`, `get_current_by_path`, `get_by_variant_group`, `get_file_by_id`, `update_file_status`, `recalc_is_current` |
| `core/hasher.py` | SHA-256 блоками по 8192 байта, `compute_variant_group`, `process_file_entry` |
| `core/parsers/stamp_parser.py` | разбор штампа из колонтитула |
| `core/parsers/docx_parser.py` | таблицы, очистка ячеек, шапки, CSV |
| `core/doc_converter.py` | `.doc` -> `.docx` через Word |
| `scripts/process_folder.py` | сквозной прогон папки |
| `convert_doc.py` | массовый прогон папок с записью в xlsx |

Поиск файлов в потоках и API для GUI — в `docs/stage3.md`. Статусы файлов
(`SAVED`, `ERROR` и др.) теперь берутся из `core/statuses.py`.

## Версии документов

Документ определяется штампом, а не путём: `doc_code` + `revision` +
`revision_date` дают `variant_group`. `process_file_entry` возвращает:

- `NEW` — такого `doc_code` ещё нет;
- `ALREADY_EXISTS` — те же реквизиты и тот же хэш (копия в другой папке тоже);
- `NEW_VERSION` — новая версия; прежние версии получают `is_current = 0`;
- `NEW_VARIANT` — те же реквизиты, другой хэш; обе записи остаются текущими,
  выбирает пользователь.

## Штамп

`parse_stamp(path)` возвращает: `doc_code`, `project_code`, `section_code`,
`doc_type`, `revision`, `revision_date`, `revision_date_source`, `sheet`,
`sheets_total`, `stage`, `organization`, `object_name`, `title`,
`document_name`, `executors` (должность, ФИО, подпись, дата), `stamp_profile`,
`filename_dates`, `discrepancies`, `stamp_raw`, `stamp_status`.

`stamp_raw` — JSON с таблицами штампа для отладки; программа его не читает.
Подряд идущие одинаковые непустые значения в строке (от объединённых ячеек)
хранятся один раз (`_collapse_table`), пустые ячейки остаются на местах.
Реквизиты считаются по несхлопнутым таблицам и от этого не зависят.

- **Профили штампа:** `full` (ИСВН, три блока названий), `short` (ЭС1, один
  блок; титул отделяется по фразе «N этап строительства»), `unknown`.
- **Шифр:** пробелы вокруг дефисов убираются; тип документа может содержать
  цифры (`.В4`). Шифр без типа получает `doc_type = XN` (виртуальный тип);
  в `doc_code` `.XN` не дописывается.
- **Дата:** штамп, затем имя файла, затем дата последнего изменения файла;
  источник в `revision_date_source` (`stamp` / `filename` / `modified`).
- **Расхождения** штампа с именем файла (дата, номер «Изм.N») парсер не
  исправляет, а пишет в `discrepancies`: решает пользователь.
- **stamp_status:** `OK`, `PARTIAL`, `MISSING`, `UNSUPPORTED`.
- Для ИСВН `revision = 1` («Изм. 1, Нов.»), ТЗ приведено в соответствие.

## Таблицы и CSV

`extract_tables_from_docx` берёт таблицы через `docx2python`;
`clean_cell_text` склеивает абзацы и списки в строку без переносов;
`extract_headers` собирает шапку из нескольких строк, отбрасывает строку
нумерации и раскрывает групповые заголовки; `save_table_to_csv` пишет
`data/exports/{hash[:16]}_table_N.csv` в `utf-8-sig`, пути идут в
`files.csv_path` через `;`, статус файла становится `SAVED` (или `ERROR`).

### Многоуровневые шапки и профили (кабельный журнал)

Если над колонками есть ячейки, объединённые по горизонтали, шапка считается
иерархической: каждый уровень приводится `normalize_header`
(`core/transformer/schema_analyzer.py`), одинаковые подряд идущие уровни
схлопываются, уровни склеиваются через `|`:
`КабельПровод|ПоПроекту|КолЧислоИСечЖил`. Если нормализованное имя уровня
длиннее 15 символов, слова начиная с третьего усекаются до 3 символов
(ТЗ Этапа 2, п. 2.1). Плоские шапки (ВОР)
остаются как в документе. Название таблицы на всю ширину («ВЕДОМОСТЬ ОБЪЁМОВ
РАБОТ») в шапку не входит.

`parse_table` (`core/parsers/header_profiles.py`) определяет профиль шапки
и чистит колонки: `generic`, `cable_basic` (9–10 колонок), `cable_section`
(11, «Участок трассы кабеля»), `cable_pipes` (17, «Проход через» и бирки),
`unknown` (иерархическая шапка не кабельного журнала). В кабельных профилях
блок «Проложен» (в `cable_section` с вторым «Участком трассы кабеля») — заготовка
для заполнения по факту: он не используется и не выгружается никогда, даже
если в нём есть данные (решение пользователя; в файле 04 заполнено 6 строк из
128, они теряются осознанно). Пустые колонки-артефакты и пустые строки
убираются. Строки-разделы («КЛ-6кВ») остаются в данных для Power Query.

Приведение колонок одинакового назначения к единым каноническим именам и
порядку (общая схема КЖ для объединения файлов в один CSV) в Этап 1 не входит.
Это Этап 2: сначала проверяется fuzzy-маппинг (rapidfuzz, порог 85); если он
ошибается, составляется таблица синонимов. Колонки, которых нет в части
профилей (например, бирки только в `cable_pipes`), в общем CSV остаются
пустыми у остальных файлов.

## Обслуживание БД и папки CSV

Код: `core/exports.py`, вызывается из `scripts/process_folder.py` через `main.py`.

- CSV и отчёты `_report_*.tsv` пишутся в `data/exports/<имя_бд>/`
  (для `data\new.db` это `data\exports\new\`). Источник истины — БД:
  актуальный CSV — тот, чей путь есть в `files.csv_path`.
- `python main.py --db data\new.db --prune` — только показывает: сирот
  (CSV в папке БД без записи), битые ссылки (запись есть, файла нет),
  CSV этой БД в старой общей папке `data\exports` и CSV в корне, не нужные
  ни одной `.db` из `data\`.
- `--prune --apply` — сирот переносит в `<папка БД>\_orphans\`, CSV этой БД
  из общей папки — в папку БД (если на файл ссылается другая БД, он
  копируется), ничьи CSV из корня — в `data\exports\_legacy\`. Ничего не
  удаляется; отчёты не трогаются.
- `python main.py --db data\new.db --drop-db` — переносит в
  `data\archive\<имя>_<время>\` сначала CSV из БД, потом остальные файлы её
  папки, потом саму БД (с `-wal`, `-shm`, `-journal`).
  `--no-archive` удаляет насовсем, `--dry-run` только показывает план.
- Тесты: `tests/test_exports.py`.

## Тесты

72 теста в `tests/` (кроме теста записи в xlsx): хэш и четыре сценария версий, очистка ячеек, шапки, CSV,
сквозной прогон на собранном вручную docx, штамп ИСВН и ЭС1 на реальных файлах,
правила даты. Часть тестов использует реальные файлы из папки `ВОР`.

## Известные ограничения

- Групповые шапки с объединением на реальных ВОР проверены не полностью:
  стоит открыть несколько CSV в Excel.
- Короткий профиль штампа опирается на эвристику («N этап строительства»).
- После правки `extract_tables_from_docx` CSV в `data/exports` нужно
  перегенерировать (`python main.py ВОР`).
